## 🔴 确认 bug

### R1. `_refresh_updated_at_from_sqlite` 在 8.2 主库上必然抛错且被静默吞掉 —— issue-0183 修复已完全失效

- **位置**：`token_dashboard_server.py` L956-1001（查询 L990，静默吞错 L993-994）
- **证据**（只读实测，2026-09-11 01:00）：
  - 实查全部 **12/12** 个 agent 的 `~/.openclaw/agents/<aid>/agent/openclaw-agent.sqlite`，**均无 `sessions` 表**（8.2 schema 改为 `session_windows` / `session_transcript_active_events` / `conversations` 等 60+ 张新表）
  - 代码 L990 执行 `SELECT session_key, updated_at FROM sessions` → 每次都抛 `sqlite3.OperationalError: no such table: sessions`
  - L993-994 `except Exception: continue` **静默吞掉，零日志**
- **触发条件**：sessions 缓存每 15 秒刷新一次（L1007），每次对每个 agent 执行该查询 → 100% 必败
- **影响链**（issue-0295「9-7 复发」的直接根因，与 issue-0295 记录第 3 条怀疑完全吻合）：
  1. CLI `sessions --json` 对 subagent session 的 updatedAt 滞后（0183 已实测的原始问题）
  2. sqlite 真值覆盖因本 bug 失效 → updatedAt 维持滞后值
  3. WS 对 subagent run 本来就不发 hasActiveRun（0183 实测）
  4. 双信号同时失明 → 正在跑子任务的 agent 被判 waiting/idle
- **修复方向备注**（未动代码）：8.2 的 `session_windows` 表有同构字段，`SELECT session_key, updated_at FROM session_windows` 即为对应替换；另该表还有 `transcript_updated_at`（比 `updated_at` 更贴近写入时间）可评估。

## 🟡 疑似风险

### Y1. WS 重连 sync 先清空状态、后等响应 —— sync 失败窗口内所有活动状态归零
- L1147-1148：`_agent_active_runs.clear()` / `_agent_ws_activity.clear()` 在 `sessions.list` 响应回来**之前**执行；若 sync 响应超时（L1105 `wait_for timeout=10`）抛异常 → 状态已丢、直接跳外层重连
- Gateway 每天 04:00 定时重启（crontab 有该任务）→ 每天必经一次该窗口；叠加 R1 死亡 → 重连窗口内正在干活的虾全部显示错误状态

### Y2. 重连 sync 数据源覆盖面依赖 `sessions.list` 的 hasActiveRun —— 对 subagent run 未验证
- issue-0183 已实测「Gateway 对 subagent run 不发 sessions.changed(hasActiveRun=True)」；若 `sessions.list`（L1108-1128）同样不含 subagent run 标记，重连后正在跑子任务的虾全部漏判。0183 靠 sqlite 覆盖兜底，现在兜底已死（R1）
- 本审查无法在不连 WS 的情况下验证该 RPC 行为，标记为待验证

### Y3. `_agent_active_runs` 按 agentId 收敛多 session 状态 —— 并发会话互相覆盖
- L1210-1220：sessions.changed 按单 session 发 hasActiveRun，但字典按 agentId 存/删。主会话 run 结束（False）会 pop 整个 agent 的标记，即使另一 session（cron/心跳/子代理）还在跑 → working→idle→working 抖动
- 正确做法需按 sessionKey 维度存或引用计数（仅备注，未改）

### Y4. `_read_session_transcript` Phase1 异常时静默回退 Phase2 读 .bak/.reset 旧 jsonl —— 可能返回远古模型数据
- L342-410：Phase1 sqlite 抛错（如 db 短暂锁住）→ 静默落到 Phase2；实测 `main/sessions/` 下已**无活跃 .jsonl**（8.2 全进 sqlite，目录里只剩 `.bak-*` / `.deleted.*.zst` / trajectory-path）→ 可能读到数周前的 assistant 消息 → 模型分布显示远古模型，无任何「数据是旧的」标记
- 与 0266 记录的「CLI 子进程静默回退旧缓存」同一模式：fallback 无标记、无日志
- 现状缓解：`transcript_events` 表仍在且结构未变（实测有数据、`message.model` 字段齐全），常规路径正常，风险仅在锁/异常窗口

### Y5. `_get_cached_sessions` CLI 失败回退旧缓存，响应体无陈旧度标记
- L1013-1027：0235 已补日志（好），但 fallback 返回的 data 不带 stale 标志 → 前端无法感知这是 N 分钟前的数据；gateway 长时间不可用时看板定格且界面无提示（0266 的界面层复现路径仍在）
- 另：缓存过期后并发请求无 in-flight 去重（check-then-refresh 非原子），多客户端同时轮询会重复 spawn CLI 子进程

### Y6. WS token 只在线程启动时读一次 —— token 轮换后 WS 永久失联
- L1063：`token = _get_gateway_token()` 在外层重连循环**外**。token 失效 → connect 永远失败，每 10s 空转重试，永不重读 openclaw.json。服务进程已连跑 3 天+，此类「只读一次」配置随时间累积风险

### Y7. `_find_gateway_pids` 子串匹配过宽 —— 非Gateway进程可被误认为 Gateway
- L1293-1302：命令行同时含 `openclaw/dist/index.js` 和 ` gateway` 即认定。实测该逻辑会误匹配「命令行里引用了这两个字符串」的巡检/grep/zsh 包装进程（本审查的测试进程即被误配）
- 影响小（瞬时、误配进程通常无子进程），但会造成 exec 归因在误判窗口内失真；且与 `_gateway_health`（L509，要求 `' gateway '` 带尾空格）口径不一致

### Y8. `merge_with_snapshot` 快照条目不存 updatedAt —— `_trim_snapshot_data` 排序失效
- L931-938 写入快照的 6 字段无 updatedAt；L913-919 trim 时按 `s.get('updatedAt', 0)` 排序恒为 0 → 超 500 条时裁剪退化为按插入序，可能裁掉活跃 session、保留死 session。当前量级未触发（<500），属定时炸弹

### Y9. `_memory_watchdog_loop` 用 ru_maxrss（历史峰值）当当前 RSS
- L198-235：macOS `ru_maxrss` 是进程生命周期**最大值**，非当前值。进程历史冲高后读数永久不降 → ① >400MB 分支每次 gc 后日志照样报高读数（刷无效 warning）；② 一旦历史峰值超 800MB，看门狗会每 60s 自杀一次（launchd 拉起后峰值清零才恢复）。当前进程 3 天未触发说明峰值 <800MB，但语义错误真实存在

### Y10. 服务器绑定 0.0.0.0:18888 暴露到局域网所有网卡
- L2299：本机豁免逻辑（L1994-1997）依赖 client_ip=127.0.0.1 且无 CF 头，局域网直连仍需过 Cookie 认证，安全面尚可；但端口对整个局域网开放，比「仅 127.0.0.1 + cloudflaled 隧道」的预期暴露面宽

### Y11. 前端多处插值未转义（低风险注入面）
- 模板 L707 `s.model`、L878/L892 `j.name`、L977 `h.agentId||h.agentName` 直接拼 HTML。数据源均为内部 CLI/配置，攻击面小；但 cron job 名等若被污染可注入 HTML（多数其他位置已用 mEsc，口径不一致）

## 结论

- 🔴 红色 2 项（R1/R2）同一根因：**8.2 升级删掉 `sessions` 表后，两处 sqlite 查询必败且被裸 except 静默吞掉**。R1 直接解释 issue-0295 的 9-7 复发（0183 修复被升级无声打断）；R2 使定时任务模型列自 8.2 起一直显示配置值。修复面小、方向明确（换表名 `session_windows` + 失败打日志），但按指令未做任何改动。
