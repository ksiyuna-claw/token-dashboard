# Token看板 任务完结状态即时性调研报告

> 调研时间：2026-07-29
> 调研人：基围虾（CTO）
> 委托人：匡书记

---

## 一、结论先行

**当前系统对"模型正在思考"的状态检测已经很即时（秒级），但对"session 完结"的状态显示存在 15~30 秒延迟。**

延迟的核心根因是**前端 15 秒轮询 + 后端 15 秒缓存**的叠加。要降低延迟，最高性价比方案是 **SSE 推送**（已有 WS 数据源，只差推送管道），开发成本约半天。

---

## 二、现状分析

### 2.1 数据流全景

```
Gateway 内部状态
    ↓ WebSocket 事件 (sessions.changed / hasActiveRun)
看板后端 (token_dashboard_server.py)
    ├── WS 监听线程 → _agent_active_runs / _agent_ws_activity (内存)
    ├── CLI 轮询线程 → openclaw sessions --json (每15s, 缓存TTL=15s)
    └── /agent-status HTTP 端点 → 综合判定后返回 JSON
    ↓ HTTP
前端浏览器
    └── fetchAgentStatus() → setInterval(15秒) 轮询 /agent-status
```

### 2.2 各环节延迟测量

| 环节 | 延迟 | 说明 |
|------|------|------|
| WS 事件传递 | **<1秒** | Gateway → 看板后端 WS 线程，实时接收 |
| 后端缓存 `_CACHE_TTL` | **0~15秒** | `openclaw sessions --json` 结果缓存15秒 |
| CLI 执行耗时 | **~1.2秒** | `openclaw sessions --json --all-agents --limit 50` 的子进程启动+查询时间 |
| 前端轮询间隔 | **0~15秒** | `setInterval(fetchAgentStatus, 15000)` |
| Cloudflare Tunnel | **~0.1秒** | 公网访问额外延迟，可忽略 |
| **端到端总延迟** | **0~30秒，中位数~15秒** | |

### 2.3 当前状态判定逻辑（优先级链）

```
1. hasActiveRun=True (WS精确信号)        → working  【秒级，与Telegram typing同步】
2. 有活跃exec进程 (ps aux扫描)            → working  【15秒内更新】
3. WS 30秒内有事件                         → working  【30秒窗口】
4. updatedAt 90秒内                        → working  【覆盖思考窗口】
5. updatedAt 90秒~10分钟                   → waiting  【】
6. updatedAt >10分钟                       → idle     【】
```

### 2.4 痛点精确定位

**"任务完结"到看板显示"等待中/空闲"的延迟来自三个叠加：**

1. **后端 sessions 缓存（15秒）**：`_get_cached_sessions()` 的 `_CACHE_TTL = 15`。即使 session 已完结，后端最多等15秒才会刷新到新状态。
2. **前端轮询间隔（15秒）**：前端固定15秒请求一次，不关心后端是否有新数据。
3. **hasActiveRun 清除依赖 WS 事件**：`sessions.changed(hasActiveRun=false)` 事件到达后，`_agent_active_runs` 字典立即清除。这部分是秒级的。

**实际表现**：
- 模型回复完成 → hasActiveRun=False 事件秒级到达后端 → `_agent_active_runs` 立即清除 ✅
- 但前端最多等15秒才下次轮询 → 看板最多再显示"工作中"15秒 ❌
- 加上后端缓存刷新 → 极端情况可达 **30秒延迟**

## 三、延迟根因总结

| 根因 | 影响 | 严重度 |
|------|------|--------|
| **前端固定15秒轮询** | 完结后最多等15秒才请求新状态 | 🔴 主要原因 |
| **后端15秒 sessions 缓存** | 即使前端请求了，也可能拿到旧数据 | 🟡 次要原因 |
| **CLI 子进程开销** | `openclaw sessions --json` 每次约1.2秒 | 🟢 可接受 |
| **Cloudflare Tunnel** | ~0.1秒，公网访问 | 🟢 可忽略 |

## 四、可行性评估与技术方案

### 方案A：缩短轮询间隔（最简单，治标）

**改动**：前端 `setInterval` 从15秒→5秒；后端 `_CACHE_TTL` 从15秒→5秒。

| 维度 | 评估 |
|------|------|
| 延迟改善 | 30秒 → 10秒（中位数5秒） |
| 开发成本 | 改2行代码，10分钟 |
| 性能影响 | `openclaw sessions --json` 调用频率3x，每次1.2秒CPU → 每5秒一次1.2秒子进程，CPU占用~24% |
| 风险 | CLI子进程高频启动可能影响Gateway响应（尤其有多个浏览器同时打开时） |
| 推荐度 | ⭐⭐⭐ 过渡方案 |

### 方案B：SSE 推送（推荐方案）

**原理**：后端通过 Server-Sent Events 主动推状态变化给前端，前端不需要轮询。

**架构变化**：
```
WS 线程收到 sessions.changed(hasActiveRun=false)
    ↓ 同时
    ├── 更新 _agent_active_runs（现有逻辑）
    └── 向所有 SSE 客户端广播 {agentId, status} （新增）
```

| 维度 | 评估 |
|------|------|
| 延迟改善 | 30秒 → **<2秒**（WS事件到达即推送） |
| 开发成本 | 新增 `/events` SSE 端点 + 前端 EventSource 替代 setInterval，约半天 |
| 性能影响 | 减少无意义轮询，CPU反而降低（不再每15秒fork子进程） |
| 维护复杂度 | 低。SSE 是标准HTTP，不需要额外组件 |
| 前置条件 | ✅ `ThreadingHTTPServer` 已启用（每个连接独立线程，不阻塞） |
| 推荐度 | ⭐⭐⭐⭐⭐ 最佳方案 |

**具体实现要点**：
1. 新增 `/events` 端点，返回 `text/event-stream`
2. WS 线程收到 `sessions.changed` 事件时，写入全局 SSE 队列
3. `/events` handler 从队列读消息，`Content-Type: text/event-stream` + `Cache-Control: no-cache`
4. 前端用 `new EventSource('/events')` 替代 `setInterval(fetchAgentStatus, 15000)`
5. SSE 作为实时推送（状态变化），保留15秒轮询作为降级 fallback（SSE断连时仍能刷新）
6. 轮询数据源不需要变：sessions --json 缓存继续保留，但只作为 SSE 断连时的兜底

**降级策略**：SSE 连接断开 → 前端检测到 → 回退到15秒轮询模式

### 方案C：WebSocket 双向推送（过度工程）

**原理**：前端直接连 Gateway WS（或后端建 WS 服务），实时推送。

| 维度 | 评估 |
|------|------|
| 延迟改善 | 与方案B相同（<2秒） |
| 开发成本 | 比SSE高，需额外实现WS服务端 + 心跳/重连逻辑 |
| 维护复杂度 | 中。WS 长连接管理、断连检测比SSE复杂 |
| 推荐度 | ⭐⭐ 不推荐。SSE 已够用，WS是杀鸡用牛刀 |

### 方案D：腾讯云中转 + SSE（旧方案回顾）

匡书记 2026-07-08 曾提出此方案，解决公网访问 + 延迟问题。

**现状变化**：
- 公网访问已通过 Cloudflare Tunnel 解决（`token-dashboard.crypto-signal.work`）✅
- 认证已加（JWT Cookie + 密码登录）✅
- `ThreadingHTTPServer` 已启用 ✅

**结论**：腾讯云中转方案的前提条件已部分自愈。当前不需要腾讯云，直接在Mac mini上做SSE即可。

## 五、推荐方案与执行计划

### 推荐：方案B（SSE 推送）

**理由**：
1. 延迟从30秒降到<2秒，解决痛点
2. 开发量小（半天），不引入新依赖
3. CPU反而降低（减少无意义轮询）
4. 降级策略清晰（SSE断 → 回退轮询）
5. 前置条件全部满足（ThreadingHTTPServer + WS数据源 + 认证）

### 执行计划（分3步）

**Step 1：后端新增 `/events` SSE 端点**（~2小时）
- 全局 SSE 客户端管理器（`threading.Lock` 保护的 client set）
- WS 线程收到 `sessions.changed` 事件时，调用广播函数
- `/events` handler：`Content-Type: text/event-stream`，长连接，每30秒发心跳
- 关键：SSE handler 要在 `_require_auth()` 通过后才允许连接

**Step 2：前端改用 EventSource**（~1小时）
- `new EventSource('/events')` 监听状态变化
- 收到推送 → 更新 `_agentStatusMap` → 立即重新渲染
- 保留 `setInterval(fetchAgentStatus, 15000)` 作为 SSE 断连降级
- SSE 连接状态指示器（已连接/降级轮询中）

**Step 3：验证 + 灰度**（~1小时）
- 本机验证：spawn 一个子agent，观察看板状态变化延迟
- 验证 SSE 断连降级：手动 kill SSE 连接，确认轮询接管
- 验证多客户端：多个浏览器同时打开，确认都能收到推送

## 六、注意事项与风险

| 风险 | 缓解 |
|------|------|
| SSE 长连接占用线程 | ThreadingHTTPServer 每连接独立线程，当前并发量极低（1-3个浏览器），无问题 |
| Cloudflare Tunnel 对 SSE 的兼容性 | Cloudflare 默认支持 SSE（有100秒超时，但心跳保活即可解决） |
| 内存泄漏（客户端断开未清理） | 全局 client set + 定期清理已断开连接 |
| sessions --json 数据仍然15秒刷新 | SSE 只推"状态变化事件"（working→idle），不推完整数据。完整数据仍靠轮询补充 |

## 七、补充发现

### 7.1 `openclaw sessions --json` 已暴露 `status` 字段
session 有 `status: 'running' | 'done' | 'killed'` 字段。当前看板**未使用**此字段，而是依赖 hasActiveRun + 进程检测 + updatedAt 时间戳组合判定。

这个字段可以作为辅助信号：当 `status` 从 `running` → `done` 时，也是"完结"的精确信号。但由于 CLI 数据本身有15秒缓存延迟，不如 WS 的 `hasActiveRun` 实时。

### 7.2 hasActiveRun 的可靠性
`hasActiveRun` 来自 Gateway 内部的 `chatAbortControllers`，与 Telegram typing indicator 共用同一机制。**这是目前最可靠的实时状态信号**，延迟<1秒。

### 7.3 子代理 session 残留问题
已通过 crontab 兜底清理解决（每天07:00），不影响状态即时性。
