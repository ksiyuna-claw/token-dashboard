# Token 看板产品说明书

> 最后更新：2026-07-09

## 产品定位

虾厂的统一监控看板。实时展示 Agent 工作状态、模型 Token 额度、系统健康指标和定时任务运行情况。
设计目标：匡书记在 iPad 上打开网页就能看到整个虾厂的运行状况，不需要主动去查。

## 访问方式

- **公网（密码保护）**：`https://token-dashboard.crypto-signal.work/`
  - 用户名：`kuangsiyu`
  - 密码：与量化看板相同（`DASHBOARD_PASSWORD`，见量化看板 `.env`）
  - 认证方式：HTTP Basic Auth（浏览器会自动弹出密码框）
- **局域网**：`http://<Mac-mini-IP>:18888/`
- **本机**：`http://127.0.0.1:18888/`（无认证，方便调试）
- 服务进程：`com.openclaw.token-dashboard`（LaunchAgent，开机自启）

## 页面结构

### 1. 🦐 虾厂员工
每只虾一张卡片，包含：
- **工作状态**：🔨 工作中（2分钟内有活动）/ ⏳ 等待中（10分钟内）/ 😴 空闲
- **状态排序**：工作中的排最前面
- **模型**：当前使用的模型 + 供应商标签
- **Token 数据**：输入/输出/上下文使用率
- **分身数量**：📎 紫色标注该虾有几个 subagent 在跑
- **Tab 筛选**：主会话/心跳/子代理/Slash/微信Bot/系统/全部

数据来源：`openclaw sessions --json` + `/agent-status` 端点
刷新频率：**每 15 秒**（前端 JS 轮询，不消耗 Token）

### 2. 📦 模型供应商额度
展示各供应商（智谱国内/海外、DeepSeek、**MiniMax 编程套餐**、**阿里云百炼 DashScope**）的额度使用情况：
- 使用百分比 + 进度条
- 颜色判定：🟢 安全 / 🟡 偏快 / 🟠 危险 / 🔴 已停
- 恢复倒计时

数据来源：供应商额度 API（后端代理转发，避免前端跨域/代理问题）
刷新频率：**每 60 秒**

> MiniMax 额度端点 `GET api.minimaxi.com/v1/token_plan/remains`（**走代理**，实测直连频繁超时）。返回的是「剩余%」，看板已转为「已用%」；general=文本/代码模型（M3），video 不展示。

### 3. 🩺 系统健康
CPU、内存、Swap、磁盘、系统负载、CDP Chrome 异常检测。

数据来源：`/health-json` 端点（读本地 ps/vm_stat/df/uptime）
刷新频率：**每 30 秒**

### 4. ⏱ 定时任务
分四个子板块：
- **OpenClaw 定时任务**：各虾的 cron job（语义任务）
- **系统 Crontab**：纯脚本定时任务，标注 `[项目名] 用途`
- **系统服务**：LaunchAgent 服务状态
- **Web 前端轮询**：看板自身的刷新频率说明

刷新频率：**每 60 分钟**（定时任务变化频率低）

### 5. 📊 总览
员工总数、Session 数、Token 汇总。

## 技术架构

```
iPad 浏览器（前端 JS 轮询）
    ↓ HTTP
Python HTTP 服务（18888 端口）
    ├── 读本地 session 文件（openclaw sessions --json）
    ├── 调供应商 API（智谱/DeepSeek）
    ├── 读系统指标（ps/vm_stat/df）
    └── 读 crontab + launchctl
```

- **后端**：`token_dashboard_server.py`（单文件 Python HTTP 服务）
- **前端**：`token_dashboard.html`（单文件，内联 CSS/JS）
- **部署**：LaunchAgent `com.openclaw.token-dashboard`，KeepAlive=true
- **零 Token 消耗**：所有数据采集都是本地命令或 API 调用，不经过 LLM

## 已知问题与修复记录

### 2026-06-19：Token用量推送重复发送

**现象**：07:07 推送时匡书记收到 4 条消息（报告×2 + 失败告警×1 + done×1），同一份报告发了两遍。

**根因**：双重发送路径。
- 推送脚本 `token_usage_push.py` 自带 curl 发 TG 消息（脚本最后一行）
- OpenClaw cron 的 `delivery.mode=announce` 也会发一次
- 第一次：脚本 curl 发送成功（#5633 送达），但 OpenClaw delivery 层 sendMessage 网络超时 → 标记 delivery failed
- OpenClaw 自动发失败告警（#5634）
- OpenClaw 自动重试 cron → 脚本再跑一遍 → curl 又发一次（#5635 送达）
- Agent 回复 done（#5636）

**修复**：将 cron job `cabb4d73-b613-4127-af29-317a4be68aac` 的 `delivery.mode` 从 `announce` 改为 `none`。脚本自带通知，不需要 OpenClaw 重复发送。

**教训**：当脚本自带通知能力时，cron job 的 delivery 必须设为 `none`，否则会导致双重发送 + 误报失败。

### 2026-06-19：子代理 session 残留堆积（125 个）

**现象**：看板上显示大量子代理 session，实际早已完成任务。

**根因**：OpenClaw 的子代理自动归档靠内存定时器（`archiveAfterMinutes: 30`），Gateway 重启后定时器丢失，session 永久残留。文档明确写了 "pending timers are lost if the gateway restarts"。

**修复**：在每天 07:00 的清理脚本中增加 `[12] OpenClaw 子代理 session 清理`，直接操作各 agent 的 `sessions.json`，归档超过 1 小时的已完成子代理 session。不依赖 Gateway 内存定时器。

**清理效果**：首次清理 123/127 个残留。

### 2026-06-19：看板工作状态检测不准（updatedAt 过时）

**现象**：皮皮虾/斑节虾明明在干活（跑 Kling 生图、蒸馏脚本），看板显示空闲或等待。

**根因**：`openclaw sessions --json` 的 `updatedAt` 字段在 agent 执行 tool call（如 `process poll`）时不更新。agent 在等待后台任务完成的整个过程中，`updatedAt` 停留在最后一次消息落盘的时间，可能滞后 10+ 分钟。

**修复**：在 `/agent-status` 端点增加进程检测（`_detect_active_process_agents()`）。每次请求时跑一次 `ps aux`，按工作目录关键字匹配进程所属 agent。有活跃 exec 进程（python/node/ffmpeg）→ 直接判定为 working，覆盖 `updatedAt` 的判断。

**判定优先级**：
1. 有活跃 OS 进程 → 🔨 working（最高优先级）
2. `updatedAt` 2 分钟内 → 🔨 working
3. `updatedAt` 10 分钟内 → ⏳ waiting
4. 其余 → 😴 idle

**性能影响**：`ps aux` 约耗时 5ms，对 15 秒轮询无感知。

### 2026-06-20：WS 监听功能修复（sessions.subscribe + minProtocol）

**现象**：看板的 WebSocket 监听功能自上线以来一直是死功能，`wsConnected` 始终为 False。

**根因**（两轮修复）：

第一轮（#1）发现三重 bug：
1. `connect` RPC 使用 `minProtocol: 4`，但 Gateway schema 要求 `minProtocol: 3` 才能通过验证（`ok: false`）
2. connect 响应未检查 `ok` 字段，只检查了 `type == 'res'`，错误地继续执行
3. connect 成功后未调用 subscribe，Gateway 不广播事件

第二轮（#2）CEO实测发现方法名错误：
1. 第一轮用的 `chat.subscribe` 方法 Gateway 根本不支持（返回 `unknown method: chat.subscribe`），正确方法是 **`sessions.subscribe`**
2. scopes 缺少 `operator.admin`，导致权限不足
3. 需要监听 `session.message` 和 `sessions.changed` 事件（subscribe 后实际推送的事件类型）

**修复**：
- `minProtocol` 改为 3
- connect 后追加 `sessions.subscribe` 调用（非 `chat.subscribe`）
- scopes 追加 `operator.admin`
- 新增 `session.message` 和 `sessions.changed` 事件监听
- 配置 `logging.basicConfig` 使 WS 调试日志输出到 launchd 日志

**验证**：重启后 `wsConnected: True`，15秒内收到9个非health事件（session.tool/session.message/agent），涵盖 jiweixia 和 pipixia 两个活跃 agent。

## Agent工作状态检测演进史（踩坑全记录）

### V1：纯时间戳（2026-06-18）
- **方案**：`openclaw sessions --json` 的 `updatedAt` 字段，120秒内=working，600秒内=waiting，更久=idle
- **问题**：模型思考期间updatedAt不刷新 → 工作中的虾被误判为waiting
- **发现场景**：皮皮虾/斑节虾跑Kling生图、蒸馏脚本时，看板显示空闲

### V2：+进程检测（2026-06-19）
- **新增**：`ps aux` 扫描python3/node/ffmpeg进程，按workspace目录匹配agent
- **效果**：有exec进程的虾能准确显示working
- **遗留问题**：纯模型对话（无exec进程）仍然检测不到

### V3：+WS监听（2026-06-19→06-20，四轮修复）

#### 第一轮：WS基础连接
- **目标**：连Gateway WS，实时收chat事件
- **Bug 1**：`minProtocol: 4` 应为 `3`，connect RPC从未真正成功
- **Bug 2**：connect响应只检查type没检查ok字段，错误继续执行
- **Bug 3**：没有logging，所有错误被静默吞掉

#### 第二轮：subscribe调用
- **目标**：connect成功后subscribe才能收到事件
- **Bug 4**：用了 `chat.subscribe`——Gateway根本没有这个方法（返回 `unknown method`）
- **正确方法**：`sessions.subscribe`（通过打印Gateway的189个可用methods发现）

#### 第三轮：scope + 方法名
- **Bug 5**：scopes缺少 `operator.admin`，权限不足
- **Bug 6**：subscribe后实际推送的事件类型是 `session.message` 和 `sessions.changed`，不是原来监听的 `chat`
- **修复**：全部改正，15秒内收到9个非health事件 ✅

#### 第四轮：停止检测延迟
- **问题**：启动检测5秒OK，停止检测61秒太慢
- **根因**：WS TTL=30秒 + updatedAt阈值=60秒，取较长者
- **修复**：WS TTL 30→10秒，updatedAt阈值 60→20秒
- **效果**：停止检测从61秒降至24秒（匡书记实测）

### 最终架构：三维度状态判定
```
优先级1：进程检测（ps aux，有exec进程=确定working）
优先级2：WS事件（sessions.subscribe，10秒内有事件=working）
优先级3：updatedAt时间戳（20秒内=working，600秒内=waiting，更久=idle）
```

### 关键教训
1. **不要猜API方法名**：先打印可用methods列表，再选
2. **检查响应ok字段**：只看type=res不够，ok=false也是res
3. **加logging**：WS调试信息不输出=问题被吞掉=浪费时间排查
4. **OpenClaw WS事件不是自动广播的**：必须调sessions.subscribe才能收到
5. **chat事件方法名在不同OpenClaw版本可能不同**：文档写的`chat.subscribe`在实际API中不存在
